
1.What is the difference between HTTP and WebSocket communication? Draw the flow of each in text/arrows.

HTTP:

HTTP follows a request-response model. The client sends a request, the server responds, and that communication is 
generally finished.

Client
  │
  │  HTTP Request
  ▼
Server
  │
  │  HTTP Response
  ▼
Client
  │
  └── Connection/request completed

For example, when the customer places an order:

React
  │
  │ POST /api/orders
  ▼
Flask
  │
  │ Save order
  │
  │ Response
  ▼
React

The server cannot normally send a new message to the React application later unless the client makes another request.

WebSocket / Socket.IO:

WebSocket communication keeps a persistent connection open. Both the client and server can send events whenever needed.

React                         Flask
  │                             │
  │──── Connect ───────────────►│
  │◄──── Connection open ───────│
  │                             │
  │──── Event ─────────────────►│
  │◄──── Event ─────────────────│
  │                             │
  │◄──── New notification ──────│
  │                             │
  │──── Event ─────────────────►│
  │                             │
  └──────── Persistent connection

In my project:

Customer places order
        │
        ▼
Flask saves order
        │
        ▼
Flask emits new_notification
        │
        ▼
Admin's React app
        │
        ▼
Notification appears instantly

Main difference: HTTP is primarily request → response, while WebSockets allow continuous two-way communication.


2.What is a Socket.IO room and why did you use one for admin users instead of broadcasting to everyone?

A Socket.IO room is a logical group of connected clients. A socket can join a room, and the server can send an event 
specifically to that room.

In my application, admin join:

admin

When an admin connects:

Admin 1 ──┐
Admin 2 ──┼──► "admins" room
Admin 3 ──┘

When a new order is created, the backend does:

socketio.emit(
    'new_notification',
    notification_data,
    room='admins'
)

The event is therefore delivered to the connected sockets in the admins room.

Why not broadcast to everyone?
If you broadcast to everyone:

New order
   │
   ├──► Admin
   ├──► Customer A ❌
   ├──► Customer B ❌
   └──► Customer C ❌

Customers would receive an admin-specific notification.

With the admin room:

New order
   │
   ▼
admins room
   ├──► Admin 1
   ├──► Admin 2
   └──► Admin 3

So the room provides targeted communication and avoids sending irrelevant or potentially sensitive notifications to other users.


3.When a user refreshes the page,the socket disconnects and reconnects.How do previously saved notifications still appear in the bell dropdown?

The WebSocket connection itself does not preserve the notification data.

When the user refreshes:

Browser refresh
      │
      ▼
Old Socket.IO connection closes
      │
      ▼
React creates a new connection
      │
      ▼
User joins their room again

However, my notifications were also saved permanently in the notifications database table.

When NotificationBell mounts, it calls:

GET /api/notifications

The backend retrieves the user's saved notifications from the database:

Database
   │
   │ SELECT notifications
   ▼
GET /api/notifications
   │
   ▼
React
   │
   ▼
NotificationBell

Therefore, there are two mechanisms:

Database + REST API → preserves notification history across refreshes.

Socket.IO → delivers new notifications instantly while the application is open.

For example:

Before refresh:
Database
 └── New order #123

After refresh:
GET /api/notifications
 └──► React loads order #123
       └──► Bell displays it

This is why notifications don't disappear just because the WebSocket connection was temporarily disconnected.


4.What does socketio.emit() do versus emit() inside a @socketio.on() handler? What is the difference?

Both are used to send Socket.IO events, but they are used in different contexts.

emit() inside @socketio.on()
For example:

@socketio.on('join')
def on_join(data):
    join_room('admins')
    emit('joined', {'room': 'admins'})

Here, emit() is the contextual emit. It is used inside a Socket.IO event handler and is commonly used to respond to the 
client/event that triggered the handler.

Conceptually:

Client
  │
  │ join event
  ▼
@socketio.on('join')
  │
  │ emit()
  ▼
Client

socketio.emit()
This is called on the SocketIO server instance:

socketio.emit(
    'new_notification',
    {
        'message': 'New order #123 placed',
        'type': 'order',
        'order_id': 123
    },
    room='admins'
)

It is useful when the server needs to emit an event from application code, such as your order creation route, rather than simply responding to the currently handled socket event.

my flow is:

Customer
   │
   │ POST /api/orders
   ▼
Flask order route
   │
   ├── Save order
   ├── Save notification
   │
   └── socketio.emit()
             │
             ▼
        admins room
             │
       ┌─────┼─────┐
       ▼     ▼     ▼
    Admin 1 Admin 2 Admin 3

Simple way to remember:

emit()	                                                        socketio.emit()

*Usually used inside a Socket.IO event handler	                Can be used from general application code
*Contextual to the current Socket.IO event	                Uses the SocketIO server instance
*Useful for responding to socket events	                        Useful for application-triggered events
*Example: join → joined	                                        Example: order created → new_notification

For my project: socketio.emit() is appropriate in the POST /api/orders route because an HTTP order request triggers a 
Socket.IO notification to the admin room.
